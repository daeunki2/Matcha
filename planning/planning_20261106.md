# Matcha — Authentication API Contract

**Status:** Proposed API contract  
**Backend:** Flask / Python  
**Frontend:** Angular / TypeScript  
**Authentication:** JWT with HttpOnly Cookies

## 1. Sign-up

Page: Create Account → Register

**Front → Back**

- Request method and path: `POST /api/auth/signup`

| Field | Name | Type |
|---|---|---|
| First name | `first_name` | String |
| Last name | `last_name` | String |
| Username | `username` | String |
| Email | `email` | String |
| Password | `password` | String |

**Back → Front**

HTTP status + JSON `message`

- `202`: Request received. Please check your email.
- `400`: Please check your input.
- `429`: Too many requests. Please try again later.
- `500`: Unable to process your request. Please try again later.

**Note:**
- The backend validates the input and securely hashes the password using Argon2.
- The backend sends an email verification link.
- Return the same `202` response for an already registered email address.
- Do not reveal whether an account exists.
- Registration does not create an authenticated session.

## 2. Email Verification

Page: Create Account → Register → Receive Email → Click Verification Link → Verification Page

Frontend URL: `/verify-email?token={token}`

**Front → Back**

- Request method and path: `POST /api/auth/verify-email`

| Field | Name | Type |
|---|---|---|
| Verification token | `token` | String |

**Back → Front**

HTTP status + JSON `message`

- `200`: Your email has been verified successfully.
- `400`: Invalid verification request.
- `500`: Unable to process your request. Please try again later.

**Note:**
- The backend validates the token, expiration time, and usage status.
- The token can only be used once.
- The backend updates the user's email verification status.
- The frontend extracts the token from the URL and displays the verification result.

## 3. Login

Page: Login → Enter Username and Password → Log in

**Front → Back**

- Request method and path: `POST /api/auth/login`

| Field | Name | Type |
|---|---|---|
| Username | `username` | String |
| Password | `password` | String |

**Back → Front**

HTTP status + JSON `message`

- `200`: Login successful.
- `400`: Please check your input.
- `401`: Invalid username or password.
- `403`: Please verify your email before logging in.
- `429`: Too many login attempts. Please try again later.
- `500`: Unable to process your request. Please try again later.

**Note:**
- The backend validates the credentials and checks email verification status.
- On success, the backend issues access and refresh JWTs through HttpOnly cookies.
- Authentication tokens must not be included in the JSON response.
- The frontend requests the current user information and checks profile completion status.
- Users with incomplete profiles are redirected to `/complete-profile`.
- Users with completed profiles are redirected to `/dashboard`.

---

## 4. Get Current User

Page: Any authenticated page

**Front → Back**

- Request method and path: `GET /api/auth/me`
- Request body: None
- Authentication: Access token cookie

**Back → Front**

- `200`: Return authenticated user information.
- `401`: Authentication required.
- `500`: Unable to process your request. Please try again later.

Example `200` response:

```json
{
  "id": 42,
  "username": "alice",
  "first_name": "Alice",
  "last_name": "Smith",
  "email": "alice@example.com",
  "is_verified": true,
  "profile_completed": false
}
```

**Note:**
- The backend identifies the user from the authenticated session.
- Password hashes and sensitive authentication data must never be returned.
- The frontend uses `profile_completed` to determine navigation.
- Profile completion is validated by the backend, not trusted from a frontend-supplied value.

## 5. Refresh Session

**Front → Back**

- Request method and path: `POST /api/auth/refresh`
- Request body: None
- Authentication: Refresh token cookie

**Back → Front**

HTTP status + JSON `message`

- `200`: Session refreshed successfully.
- `401`: Session expired. Please log in again.
- `500`: Unable to process your request. Please try again later.

**Note:**
- The backend validates the refresh token and the corresponding session.
- Refresh tokens are rotated on successful refresh.
- The backend updates the authentication cookies.
- Revoked sessions must not be refreshed.
- Cookie-authenticated state-changing requests require CSRF protection.

## 6. Logout — All Devices

Page: Any authenticated page → Logout

**Front → Back**

- Request method and path: `POST /api/auth/logout`
- Request body: None
- Authentication: Session cookies

**Back → Front**

HTTP status + JSON `message`

- `200`: Logged out successfully.
- `401`: Authentication required.
- `500`: Unable to process your request. Please try again later.

**Note:**
- Logging out invalidates all active sessions belonging to the user.
- Access and refresh tokens from all devices must be rejected after revocation.
- The backend clears authentication cookies on the current browser.
- The frontend redirects the user to `/login`.
- There is no separate logout-all endpoint.

## 7. Forgot Password

Page: Login → Forgot Password → Enter Email → Send Reset Link

**Front → Back**

- Request method and path: `POST /api/auth/forgot-password`

| Field | Name | Type |
|---|---|---|
| Email | `email` | String |

**Back → Front**

HTTP status + JSON `message`

- `202`: If an account exists, a password reset email will be sent.
- `400`: Please check your input.
- `429`: Too many requests. Please try again later.
- `500`: Unable to process your request. Please try again later.

**Note:**
- The backend generates a unique, short-lived, single-use reset token.
- Only the token hash is stored in the database.
- The same `202` response is returned for registered and unregistered email addresses.
- The reset email is sent only when an eligible account exists.
- Requests must be rate-limited.
- For OAuth-only accounts without a local password, the backend must not assume that a password already exists.

## 8. Reset Password

Page: Forgot Password → Receive Email → Click Reset Link → Enter New Password

Frontend URL: `/reset-password?token={token}`

**Front → Back**

- Request method and path: `POST /api/auth/reset-password`

| Field | Name | Type |
|---|---|---|
| Reset token | `token` | String |
| New password | `new_password` | String |

**Back → Front**

HTTP status + JSON `message`

- `200`: Your password has been reset successfully.
- `400`: Invalid or expired password reset link.
- `429`: Too many requests. Please try again later.
- `500`: Unable to process your request. Please try again later.

**Note:**
- The backend validates token expiration and single-use status.
- The new password must satisfy password security requirements.
- The password is hashed using Argon2.
- The reset token is invalidated after successful use.
- All existing sessions are invalidated after the password change.
- The frontend redirects the user to `/login` after success.

## 9. Google Login — OAuth Bonus

Page: Login → Continue with Google

**Front → Back**

- Request method and path: `GET /api/auth/google`
- Request body: None

**Back → Google**

- Redirect the user to Google's authentication page.

**Note:**
- The backend initiates the OAuth 2.0 / OpenID Connect flow.
- The backend manages the OAuth client secret and validates `state` and OIDC identity information.

### Google Callback

**Google → Back**

- Request method and path: `GET /api/auth/google/callback`
- Query parameters: `code`, `state`

**Back → Front**

- Success: Set HttpOnly authentication cookies and redirect to `/auth/callback?status=success`.
- Failure: Redirect to `/login?error=oauth_failed`.
- Existing email conflict: Redirect to `/login?error=account_link_required`.

**Account handling rules:**

1. If the Google account is already linked to a Matcha user, log in to that user.
2. If no linked Google account exists and the verified email is not registered, create a new Matcha user.
3. If the verified email already belongs to an unlinked Matcha account, do not create a duplicate user and do not automatically link accounts.
4. The user must authenticate with the existing Matcha account before linking Google.
5. Newly created users with incomplete profiles are redirected to `/complete-profile`.

**Note:**
- Google accounts are identified by the provider's unique subject identifier, not by email alone.
- OAuth-only users do not require a local password.
- The backend creates the same Matcha session used for normal login.
- The frontend must not receive Google's client secret or raw authentication tokens.

## 10. Link Google Account

Page: Account Settings → Connect Google

**Front → Back**

- Request method and path: `GET /api/auth/link/google`
- Authentication: Existing Matcha session

**Back → Google**

- Redirect to Google authentication for account linking.

### Google Account Linking Callback

**Google → Back**

- Request method and path: `GET /api/auth/link/google/callback`
- Query parameters: `code`, `state`

**Back → Front**

- Success: Redirect to `/settings?google=linked`.
- Failure: Redirect to `/settings?google=failed`.

**Note:**
- The backend must validate the existing Matcha session and OAuth state.
- The backend must verify that the Google account is not linked to another Matcha user.
- Account linking requires an authenticated Matcha account.
- Sensitive account linking operations may require recent reauthentication.
- The backend stores the provider name and provider user ID in a separate account-linking table.

## 11. Shared Security Requirements

- All authentication traffic must use HTTPS in production.
- The backend must validate every request independently of Angular.
- Use parameterized SQL queries to prevent SQL Injection.
- Never execute user-controlled input as shell commands.
- Store passwords using Argon2, never in plaintext.
- Authentication cookies must use HttpOnly, Secure, and appropriate SameSite settings.
- Cookie-based authentication requires CSRF protection.
- CORS is not a substitute for authentication or authorization.
- Apply rate limiting to login, registration, and password reset requests.
- Do not expose internal errors, secrets, password hashes, or authentication tokens.
- All-device logout must invalidate existing sessions server-side.
- OAuth accounts must never be linked solely because email addresses match.
